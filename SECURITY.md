# Безопасность — Арена Переговоров

Краткий обзор того, как в MVP хранятся секреты и что ещё предстоит закрыть.

## Секреты в env

Все секреты приложения приходят через переменные окружения (см. `.env.example`, `src/config.rs`) и **не должны** попадать в git (`.env` в `.gitignore`):

| Переменная | Назначение | Требования |
|---|---|---|
| `JWT_SECRET` | Подпись JWT-токенов (access + refresh) | ≥ 16 символов; в проде — `openssl rand -hex 32` |
| `ENCRYPTION_KEY` | Мастер-ключ шифрования API-ключей провайдеров (AES-256-GCM, вывод ключа через Argon2id) | Отдельный случайный секрет в проде; иначе наследуется из `JWT_SECRET` (только dev) |
| `ADMIN_PASSWORD` | Пароль начального администратора при первом запуске | ≥ 6 символов; в проде — сложный, затем сменить в админке |

Смена `ENCRYPTION_KEY` после создания провайдеров делает сохранённые API-ключи нечитаемыми — их придётся ввести заново.

## Как хранятся API-ключи провайдеров

- API-ключи LLM/STT/TTS-провайдеров шифруются **AES-256-GCM** перед записью в SQLite; мастер-ключ в БД не хранится, только в env.
- В админ-панели и API ключи **маскируются** — полное значение никогда не возвращается клиенту после сохранения.
- В `SECURITY`-смысле БД — обычный файл: ограничьте права на файл (`DB_PATH`) и не коммитьте `*.db`.

## Остальная гигиена

- Контейнер запускается от **non-root** пользователя `arena` (см. `Dockerfile`).
- В рантайм-образ не попадают `.env`, `target/`, `*.db`, `models/` (см. `.dockerignore`).
- Ошибки upstream-провайдеров не раскрывают тела ответов клиенту (`src/error.rs` → «Внешний сервис недоступен»).
- **Rate-limit** на `POST /auth/{login,register,refresh}`: по IP (X-Forwarded-For → ConnectInfo), ответ **429** + `Retry-After`; настройка `AUTH_RATE_LIMIT_MAX` / `AUTH_RATE_LIMIT_WINDOW_SECS` (`0` — off). Счётчики in-memory (сбрасываются при рестарте).
- **CORS-allowlist**: `ALLOWED_ORIGINS` (список `https://…`); пусто — `Any` только для dev. В проде всегда задавайте allowlist.
- **Lockout** неудачных входов (per-login, в БД — переживает рестарт): после `LOGIN_LOCKOUT_MAX_FAILURES` (default 5, `0` — off) неудач в окне `LOGIN_LOCKOUT_WINDOW_SECS` учётка блокируется на `LOGIN_LOCKOUT_DURATION_SECS` → **429**; успешный вход сбрасывает счётчик. Дополняет rate-limit по IP: защита от перебора конкретного пароля.
- **Ротация refresh (single-use)**: в JWT есть `jti`; повторный `POST /auth/refresh` с тем же токеном → **401** (reuse = кража/гонка). Окно refresh после exp access-токена — `JWT_REFRESH_MAX_AGE_SECONDS` (default 7 дней, ≥ `JWT_TTL_SECONDS`). Фронтенд сериализует параллельные refresh в одну Promise.

## Отложено (deferred)

Следующие меры зафиксированы в `docs/ROADMAP.md` (этап 8, Hardening) и в MVP ещё **не реализованы**:

- пагинация, session-транзакции, LLM-quota.

## Как сообщить об уязвимости

1. **Не открывайте публичный issue** для уязвимостей с реальным impact.
2. Создайте приватный [GitHub Security Advisory](https://github.com/ApollieKastro/negotiation-arena/security/advisories) для репозитория (или напишите maintain'еру напрямую).
3. Приложите: описание, шаги воспроизведения, ожидаемое/фактическое поведение, влияние (CVSS, если знаете).
4. Ожидаемый срок первого ответа — несколько рабочих дней; до патча координацию ведём приватно.
